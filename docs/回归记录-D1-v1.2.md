## 2. D1 契约证据

### 2.1 生效拼载优先级：`config.minLoadM3ByProcess[process]` 覆盖 `Process.minLoadM3`

实现（`src/domain/min-load.ts`）：先读 `config.minLoadM3ByProcess[processCode]`，命中即返回；其后才回退 `d002MinLoadM3` → `Process.minLoadM3` → 默认 56 / `load.defaultMinM3`。`Process.minLoadM3` **不能**在 map 有值时抢先盖掉。

单测（均通过）：

- `effectiveMinLoadM3 (v1.2) > lets config.minLoadM3ByProcess override Process.minLoadM3`  
  map=30 时生效 30，同时断言种子 `PROCESSES.D002.minLoadM3` 仍为 **56**。
- `lets canonical minLoadM3ByProcess win over d002MinLoadM3`  
  map=28 且旧字段=99 → 生效 **28**。

规则引擎走同一函数：`validateFurnace` 用 `effectiveMinLoadM3(primaryProcess, ctx.config, ctx.processes)`，建议拼炉工作台传入 `effectiveMinLoadM3('D002', state.config, PROCESSES)`。

### 2.2 改配置后 `D002_MIN` 阈值立刻变化

**单测**：`D002_MIN uses effective threshold from config.minLoadM3ByProcess`  
40 m³ D002：`setProcessMinLoad(..., 30)` → **不**报 `D002_MIN`；改为 50 → warning，文案含 `50`、**不含** `56m³`。

**UI 绑定（静态）**：工作台 `index.html` 文案为「D002 最低拼载 (m³)」，`#cfgD002Min` 的 `input`/`change` 调用 `setProcessMinLoad(state.config, 'D002', n)` → `persist()` → `render()`。炉卡目标 `minTarget()` / `validateFurnace` / 建议拼炉均读 `state.config`，不是 `Process.minLoadM3`。

**浏览器（本轮补证，演示种子 P001=28 m³ @ 柜9）**：

| 步骤 | 配置 | 柜9 目标 | 炉卡「警告」 | 校验问题数 |
|------|------|----------|--------------|------------|
| 基线 | 56 | ≥56 | 有 | 4 |
| 改为 20 | 20 | ≥20（进度条变绿） | 无 | 3 |
| 改为 50 | 50 | ≥50 | 有 | 4 |

校验中心：`低于 D002 最低拼载 50m³（当前 28.0m³）`，code=`D002_MIN`，**未**再按 56 判定。

> DOM `bindNum` **缺自动化**（无 jsdom 事件单测）。本轮用浏览器补证；领域层已有 `setProcessMinLoad` → `validateFurnace` 单测。

### 2.3 兼容读取旧 `d002MinLoadM3`

单测（均通过）：

- `falls back to d002MinLoadM3 before Process.minLoadM3 when the map has no D002`（map 空、旧字段 40 → 40）
- `migrates legacy d002MinLoadM3 into minLoadM3ByProcess.D002`（`mergeConfig({ d002MinLoadM3: 40 })`）
- `persists minLoadM3ByProcess and migrates legacy d002MinLoadM3 on load`（plan-store：写出 42；仅旧字段 37 的快照读入后 map.D002=37）
- 写出仍同步旧字段：`persistableConfig` 同时带 `minLoadM3ByProcess` 与 `d002MinLoadM3`

`migrateMinLoadM3ByProcess` 还兼容非官方残留 `load.d002MinM3`，写出时剥离。

## 3. 拆炉 / TC-SPLIT-02 证据

### 3.1 单测（均通过）

| 用例 | 证明点 |
|------|--------|
| `round-trips virtualLines so split children survive reload` | plan v2 含正式字段 `virtualLines`，reload 后 `splitOf` 可解析 |
| `keeps split furnaces after reload even when the snapshot looks sparse (TC-SPLIT-02)` | 有 virtualLines 时不按稀疏演示计划清炉；`P004-A`/`P004-B` 仍挂炉次 |
| `rebuilds *-A/*-B furnaces from virtualLines if a stale wipe left them unassigned` | 炉次数组被清空时仍从 virtualLines 补回 |
| `serializes virtualLines as a first-class plan v2 field` | 快照顶层数组 |
| `rehydrates virtualLines into the pool so poolById can resolve *-A/*-B` | 池合并 |
| `does not treat a split session as a sparse demo plan` | `isPlanSparse(..., virtualLines)` → false |
| `restores missing *-A/*-B furnaces from virtualLines` | `ensureSplitFurnaces` |

`loadPlan` 在 `virtualLines.length` 时先 `ensureSplitFurnaces`，再判断稀疏；`hasPersistedSplitWork` 为 true 则不清炉。`bootApp` 用 `mergeVirtualLinesIntoPool`。
